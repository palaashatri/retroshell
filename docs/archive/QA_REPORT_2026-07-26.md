# SLOPOS-I QA Report — 2026-07-26

Independent audit and live QA of the changes made between **2026-06-19** (last known
good) and **HEAD (`a0479a8`)**. Roughly 120 commits and ~45k lines of Rust landed in
that window, none of them verified on an emulator or real machine.

**Method**

| Track | What was done |
|---|---|
| Code audit | 7 parallel area reviewers (compositor, shell core, shell system-integration, kit/render/SDK, apps, packaging/scripts, docs-vs-code) + adversarial verification of every critical/high finding. 71 raw findings → 71 after dedup → 10 verified, 0 refuted. |
| Build & test | Ubuntu 26.04 (WSL2), Rust 1.97.1, all Wayland/DRM/PipeWire dev deps. `cargo build --release --workspace`, `cargo test --release --workspace`, `cargo clippy --all-targets`. |
| Live visual QA | Xvfb 1280×800 + **labwc** (the fallback path the repo's own Docker image uses) + `slopos-shell` + first-party apps, driven by `xdotool`, ~60 screenshots across 8 runs. Wayland protocol traces via `WAYLAND_DEBUG=1`. |

**Environment limitation (important):** `slopos-compositor` **could not be executed at
all** in this environment. Its nested X11 backend hard-requires the **DRI3** X
extension, and neither Xvfb nor WSLg's Xwayland provides it; WSL2 also exposes no
KMS device (`/dev/dxg` only, no `/dev/dri/card*` until `vgem` is loaded, which is
render-only). So all compositor findings below are from code + compile verification,
**not** runtime. This same limitation is why the repo's own `Dockerfile.qa` silently
falls back to labwc — meaning **the real compositor has never been exercised by any
environment this repo ships.**

---

## 1. Headline: the tree did not build

`slopos-compositor` **failed to compile on Linux from 2026-07-11 until this audit** —
a borrow-checker error introduced by `00c53f9` ("live workspace focus + per-window
SHM paint"):

```
error[E0502]: cannot borrow `self.renderer` as mutable because it is also borrowed as immutable
   --> crates/slopos-compositor/src/main.rs:536:21
```

The entire compositor implementation sits behind `#[cfg(target_os = "linux")]`; on
macOS/Windows the file compiles to a stub `main()` that prints "Linux-only". Whoever
wrote the July 11 burst (~30 commits in a few hours) therefore never saw the error,
and the July 17 PR *"fix/compositor-build-and-audit"* fixed a **different** compile
error without catching this one.

**Consequence:** every scorecard commit after 2026-07-11 — including
`docs: goal final deep audit — honest ~85`, `docs: warpath score ~85`, and the
README's "Landed (real / live paths)" list — describes a compositor binary that
**could not be built, let alone run.** The "~85/100 daily-driver" number is not
merely optimistic; it was never measurable.

## 2. Confirmed defects (all fixed in this pass unless noted)

### Fixed

| # | Severity | Where | Defect |
|---|---|---|---|
| 1 | critical | `slopos-compositor/src/main.rs` | Linux build broken since 2026-07-11 (above). |
| 2 | critical | `slopos-compositor/src/main.rs:2020` | **The nested compositor never called `dispatch_clients`.** The listening socket only *accepts* connections; without dispatch no client request (bind, commit, …) is ever read, so every Wayland client hangs on its first roundtrip. The DRM path in `session_drm.rs:577` does this correctly — `main.rs` never did. No client could ever have painted. |
| 3 | critical | `slopos-compositor/src/main.rs` | **`wl_surface.frame` callbacks were never sent.** Frame-throttled clients (winit/wgpu — i.e. every SLOPOS-I app) draw exactly one frame and then wait forever. |
| 4 | critical | `slopos-kit/src/text_field.rs:113` | Cursor was a **char count used as a byte index**. Typing any non-ASCII character then one more panics the whole app (`String::insert` on a non-boundary). Reachable in TextEdit, AppStore, Settings, and the **lock screen password field**. |
| 5 | critical | `slopos-sdk/src/lib.rs` (`truncate_label`) | Byte-sliced UTF-8 filenames → Finder/desktop panics **every frame** a non-ASCII filename longer than 12 bytes is visible. |
| 6 | high | `slopos-compositor/src/main.rs:617` | Render elements were passed to `draw_render_elements` **back-to-front**; it expects front-to-back and occlusion-culls behind opaque elements, so z-order was inverted and opaque layers culled the windows above them. Placeholder rects were also drawn *over* real content instead of under it. |
| 7 | high | `slopos-shell/src/layer_shell_client.rs:280` | **Wayland protocol violation:** `attach_shm_markers` attached a buffer and committed *before* the first `configure` was received/acked. wlroots answers `layer_surface has never been configured` and **kills the client connection** — confirmed live in a `WAYLAND_DEBUG` trace. Restructured into create → configure/ack → attach phases. |
| 8 | high | `apps/appstore/src/main.rs` | The **INSTALL button bypassed the documented package-change gate**: `execute_transaction` checks `SLOPOS_APPSTORE_ALLOW_PACKAGE_CHANGES`, but `install_async` (what the button calls) did not — one click ran `sudo <pm> install -y`. Gate extracted into `package_changes_allowed()` and applied to both paths. |
| 9 | high | `slopos-sdk/src/lib.rs` (`paint`) | **`layout()` only ran on window resize**, never after `update()` changed content. Any dynamically-built UI kept `Rect::ZERO` and `draw_widget` skipped it — this is why the **lock screen rendered as a completely empty window** (no prompt, no password field) and why a new Terminal tab stayed invisible until resize. Now re-laid out before each paint. |
| 10 | high | `slopos-render/src/event_loop.rs:18` | `EventLoop::new().unwrap()` — the shell and every app **panicked with a raw backtrace** when no compositor was reachable. Now returns `Result`; the SDK exits cleanly with a diagnostic naming `WAYLAND_DISPLAY`/`DISPLAY`. |
| 11 | high | `slopos-sdk/src/lib.rs` (`parse_theme_preference`) | The **"eight themes" claim was false**: `solarized`, `dracula`, and `highcontrast` fell through to `_ => Classic`, so three of the eight rendered identically to Classic in every SDK app. Accents added and kept in sync with `ThemeName`. |
| 12 | medium | `slopos-shell/src/session_clients.rs` | The **plaintext lock password leaked into every spawned child app's environment** (children inherit the shell's env). Now scrubbed with `env_remove`. |
| 13 | medium | `slopos-compositor/src/main.rs:2030` | Adaptive/VRR steady-state render gate was dead code: `frame_counter % 1 == 1` is never true, so adaptive mode never rendered a steady-state frame. |
| 14 | medium | `slopos-compositor/src/main.rs:1862` | Socket handshake file was written to a hardcoded `/tmp/runtime-root/` and the socket was advertised **before** backend init, so a compositor that then failed still published a socket name the session launcher would trust. Now honors `XDG_RUNTIME_DIR` and is published only after the backend and renderer are up. |
| 15 | medium | `apps/textedit/src/main.rs` | Flaky test: two tests raced on the process-global `TEXTEDIT_FILE` env var (`cargo test` failed ~2 runs in 3). Serialized with a mutex. |

### Open — not fixed, needs the real compositor or a design decision

| # | Severity | Where | Issue |
|---|---|---|---|
| A | **critical (security)** | shell + compositor | **The lock screen does not lock a multi-client session.** Verified live: with the shell locked, launching TextEdit drew it *over* the lock screen and it accepted keystrokes (screenshot `qa7/08-bypass-check.png` — the text "SECRET-TYPED-WHILE-LOCKED" typed into an app while "Lock Screen / Incorrect password" is visible behind it). The shell's lock only covers the shell's **own surface**. A real fix needs `ext-session-lock-v1` in `slopos-compositor` (and input routing that ignores non-lock surfaces while locked); it cannot be fixed inside the shell process. |
| B | high | shell under labwc | **Keyboard input never reaches `slopos-shell` in the fallback session.** Mouse works (menus open, dock launches all 5 apps), but no shortcut fires: `Super+O` never spawns Finder, and the lock screen cannot be unlocked by typing — making "Lock Screen" a session-ending trap on the packaged path. The unlock *logic* is correct (new unit test `lock_screen_typed_password_unlocks_and_wrong_one_does_not` passes), so this is input delivery, not policy. Every shortcut in `docs/KEYBOARD_SHORTCUTS.md` is non-functional on the labwc path. |
| C | critical | `slopos-compositor/src/session_drm.rs:172` | DRM present **leaks a full-screen dumb buffer + framebuffer on every call** (`mem::forget`), re-called ~1/second — an unbounded kernel memory leak. Left alone because the DRM path cannot be tested here and a wrong fix would be worse than a documented one. |
| D | high | `slopos-compositor/src/session_drm.rs:762` | The DRM session **discards all libinput events** — zero keyboard/pointer input on bare metal. |
| E | high | `slopos-shell/src/portal_dbus.rs:624` | `option_string_loose` parses zvariant **`Debug` output**, so every string option received over the real bus is garbage. Portal Screenshot also returns success (response 0) with a `file://` URI for a file that was never created. |
| F | high | `slopos-shell/src/capture.rs` | Screenshot/record are **X11-only** (`import` / `x11grab`) in a Wayland DE — they cannot work on the session the packaging installs. |
| G | high | `slopos-shell/src/display_settings.rs:116` | The display-arrange "env bridge" sets `SLOPOS_OUTPUTS_LAYOUT` **inside the wrong process** and always reports a fabricated `1920x1080 eDP-1`. Confirmed live: the shell logs `eDP-1:1920x1080@0,0:s100` on a 1280×800 output. |
| H | high | `slopos-bus/src/transport.rs` | The IPC crate is a facade — every transport discards sends and never receives; `DBusTransport` contains no D-Bus code. |
| I | high | `apps/terminal/src/vt_parser.rs` | Claimed VT100/VT220 compatibility is missing cursor-movement CSIs (A/B/C/D/G/d), ED 0/1, and HT; DECSTBM scroll margins are dead (LF ignores `scroll_bottom`). |
| J | medium | `slopos-kit` | The toolkit's interaction layer is largely dead wiring: `Button` consumes every left-click with no hit test and has no activation mechanism; `PopupButton`/`TabView`/`Dialog` buttons cannot be clicked; `ScrollView` wheel scrolling is inert; `TextField` has no focus gating. |

A further 43 medium/low findings are recorded in the audit output (blocking subprocess
and D-Bus calls on the render thread every 5s, menu-bar status computed then discarded,

verify scripts that grep for honesty comments rather than behavior, and more).

## 3. What actually works (verified live, labwc path)

These were confirmed by screenshot, not by reading code:

- Desktop boots and renders: menu bar, icon grid (Hard Disk / Home / Applications /
  Trash), dock, and a Finder window listing the real filesystem (`/boot`, `/dev`,
  `/etc`, …).
- The Retro menu opens and renders its full item list with shortcut labels.
- The workspace switcher overlay renders and switching to Desktop 2 works
  (via menu; `Ctrl+Alt+2` does not — see finding B).
- **Multi-client launch is real**: clicking all five dock items spawned five separate
  processes (`finder`, `settings`, `textedit`, `terminal`, `appstore`), each as its own
  Wayland client with its own window.
- Terminal is a real PTY: `echo hello-slopos-i-qa` executed and its output rendered.
- TextEdit renders its toolbar, path field, editor, and live status bar
  (`Edited | No file | Ln 3 | 11w`).
- The lock screen now renders its prompt and password field, and a wrong password is
  correctly rejected with "Incorrect password" (after fix #9).
- Non-ASCII input no longer crashes (after fix #4) — though accented and CJK glyphs
  render blank, so font fallback is missing.
- The Dracula theme now renders dark (after fix #11); it previously rendered as light
  Classic. One cosmetic issue surfaced by this: **desktop icon labels are dark-on-dark
  and effectively unreadable in dark themes** — the label color is not theme-aware.
- No `zwlr_layer_surface_v1` protocol error in the `WAYLAND_DEBUG` trace after fix #7
  (28 `ack_configure` calls, connection survives).

## 5. Honest assessment

The **pure/policy layer of this codebase is genuinely good** — output-layout parsing,
workspace state, damage math, MIME planning, notification bookkeeping, package-manager
argv construction, and the idle/session policy engines are all real and well
unit-tested (544 tests). There is no command injection anywhere; every shell-out uses
argument vectors, and the Wi-Fi password is redacted before logging.

The problem is a consistent pattern: **a well-tested pure planner paired with a thin
live wrapper that was never run.** The tests pass because they test the planner. The
compositor could not compile; when it did, it never dispatched a client; when it
dispatched, it never released a frame callback. Each of those alone is fatal to
"live" — and each survived multiple rounds of self-scored audits precisely because
those audits also never ran the binary.

**The `~85/100` score should be withdrawn** — not re-negotiated downward, but treated
as unmeasured. A defensible number requires: (1) a machine with DRI3/KMS, (2) the
compositor serving `slopos-shell` and at least two app clients with real buffers on
screen, (3) keyboard input reaching the shell, and (4) `ext-session-lock-v1` before
the lock screen may be described as a lock at all.

**Recommended next steps, in order:**
1. Run `slopos-compositor` on real hardware (or any DRI3-capable X server) and confirm
   fixes #2, #3, and #6 produce a visible client window. Nothing else is meaningful
   until this passes.
2. Fix the DRM present leak (C) and DRM input drop (D) before anyone boots this as a
   session.
3. Diagnose keyboard delivery to the shell (B) — it makes the documented shortcut set
   and the lock screen unusable on the shipped fallback path.
4. Implement `ext-session-lock-v1` (A), or stop calling it a lock screen.
5. Add CI that runs `cargo build --workspace` **on Linux**. A single GitHub Actions job
   would have caught the most serious finding in this report six weeks ago.
